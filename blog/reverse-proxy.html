Reverse Proxy

Client와 Backend Server 사이의 요청 중계 구조와 구현 관점

Architecture · Network

1. 개념

Reverse Proxy는 Web Server 앞에 위치하여 Client의 요청을 Web Server로 전달하는 서버 측 중계 구조이다. Client는 실제 Backend Server와 직접 통신하는 대신 서비스 전면의 Endpoint로 요청하고, Reverse Proxy가 해당 요청을 Backend Server로 전달한다.

[출처: Cloudflare Reference Architecture, Securely deliver applications with Cloudflare]

2. 원리

Client가 보낸 HTTP/HTTPS Request는 Frontend Server의 Reverse Proxy 계층에 도달한다. Proxy는 설정된 규칙에 따라 Request를 Backend Server로 전달하고, Backend가 생성한 Response를 다시 Client에 반환한다.

[출처: Cloudflare Reference Architecture, Securely deliver applications with Cloudflare]

Client ↓ HTTPS Request Frontend Server ↓ Reverse Proxy Backend Server ↑ Response Frontend Server ↑ Client

3. 상세 설명

항목설명
Request Routing요청 경로, Host 또는 기타 조건에 따라 하나 이상의 Backend Server로 전달할 수 있다. Layer 7 Routing, Load Balancing, TLS 종료 등의 기능은 구현 제품의 지원 범위에 따라 달라질 수 있다. [출처: Microsoft Azure Architecture Center, API gateways]
Backend 분리Client가 사용하는 공개 Endpoint와 실제 Backend Server의 Host/Port를 분리할 수 있다. 내부 배치 구조를 외부 Client가 직접 알 필요가 없다.
HTTP HeaderProxy를 경유하면 Backend의 직접 연결 상대는 Proxy가 된다. Client IP, 원래 Host, Protocol 등의 정보가 필요하면 구현 제품에서 관련 Header 전달을 설정한다.
운영 고려Timeout, Connection Pool, Health Check, Logging, 장애 격리 등은 제품과 시스템 요구사항에 따라 별도 설계한다.

4. 예

NGINX + Tomcat

Client ↓ Web Server (NGINX) ↓ /api/* Reverse Proxy Frontend Server (Tomcat)
location /api/ {
    proxy_pass http://frontend-server:8080;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

NGINX의 proxy_pass와 proxy_set_header 같은 Directive는 구현 예에 해당한다. URI 전달 규칙과 Header 정책은 실제 NGINX 공식 문서를 기준으로 검증해야 한다.
