Same-Origin API Proxy

Browser의 Same-Origin Policy를 고려한 Frontend-API 배포 구성

Architecture · Network

1. 개념

“Same-Origin API Proxy”는 Web 표준에서 독립적으로 정의된 공식 Architecture Pattern 명칭으로 확인되지 않는다. 본 문서에서는 Frontend Resource와 API를 Browser 관점에서 동일한 Origin으로 노출하기 위해 Proxy를 사용하는 배포 구성을 의미한다.

Same-Origin Policy는 한 Origin에서 로드된 Document 또는 Script가 다른 Origin의 Resource와 상호작용하는 방식을 제한하는 Browser 보안 메커니즘이다. Origin은 Scheme, Host, Port로 결정된다.

[출처: MDN Web Docs, Same-origin policy]

2. 원리

Frontend와 API의 외부 URL을 동일한 Scheme, Host, Port로 제공하고 Path만 분리한다. Browser는 동일 Origin으로 판단하며, Server 측에서는 /api/* Request를 별도의 Backend Server로 Proxy할 수 있다.

[출처: MDN Web Docs, Same-origin policy]

Browser ↓ https://service.example.com ↓ Frontend Server ├→ / → Static Frontend └→ /api/* → Proxy → Backend Server

3. 상세 설명

항목설명
Origin 판단Browser가 보는 URL의 Scheme, Host, Port가 동일하면 Same-Origin이다. Path는 Origin 구성요소가 아니다. [출처: MDN Web Docs, Same-origin policy]
Server 내부 통신Browser가 접근하는 외부 Origin과 Proxy 뒤 Backend의 내부 Host/Port는 별개의 관점이다. Server 측 Proxy는 다른 내부 주소로 Request를 전달할 수 있다.
CORS와의 관계CORS는 Cross-Origin 접근을 HTTP Header로 허용하는 메커니즘이고, Same-Origin API Proxy는 Browser에 동일 Origin으로 노출하는 배포 구성이다. 두 개념은 동일하지 않다. [출처: MDN Web Docs, Cross-Origin Resource Sharing (CORS)]
Frontend 호출Frontend에서는 fetch("/api/users")처럼 상대경로를 사용할 수 있어 환경별 Backend Host를 Client 코드에 직접 넣지 않는 구성이 가능하다.

4. 예

NGINX Same-Origin API Proxy

Browser ↓ https://service.example.com Frontend Server ├→ / → Static Frontend └→ /api/* → NGINX Reverse Proxy → Tomcat + Spring REST API
// Frontend
const response = await fetch("/api/users");

# NGINX
location /api/ {
    proxy_pass http://backend-server:8080;
}

Browser가 보는 외부 URL은 https://service.example.com/api/users 이며 내부에서는 Proxy가 별도의 Backend Server로 전달할 수 있다. Same-Origin 판단은 Browser에 노출된 Scheme, Host, Port를 기준으로 한다.
