API Gateway Pattern

여러 Application Service를 위한 중앙 API 진입점과 Routing 패턴

Architecture · Network

1. 개념

API Gateway는 Client와 Application Service 사이의 상호작용을 관리하기 위한 중앙 집중식 진입점을 제공한다. Gateway는 Reverse Proxy 역할을 수행하여 Client Request를 적절한 Service로 Routing할 수 있고, 구현에 따라 Authentication, TLS 종료, Rate Limiting 등의 공통 기능을 수행할 수 있다.

[출처: Microsoft Azure Architecture Center, API gateways]

2. 원리

여러 Application Service 앞에 Gateway를 배치하고 Client에는 하나의 API Endpoint를 제공한다. Gateway는 Request를 분석해 적절한 Backend Service로 전달한다. 이 방식은 Client가 각 Service의 내부 Endpoint를 직접 관리해야 하는 결합을 줄인다.

[출처: Microsoft Azure Architecture Center, API gateways / Gateway Routing pattern]

Client ↓ API Request API Gateway ├→ User Service ├→ Order Service └→ AI Service

3. 상세 설명

항목설명
Gateway Routing하나의 Endpoint를 통해 여러 Service로 Request를 Routing한다. 예: /api/users/* → User Service, /api/orders/* → Order Service. [출처: Microsoft Azure Architecture Center, Gateway Routing pattern]
Gateway Aggregation여러 Backend Service 호출 결과를 Gateway가 결합하여 하나의 Response로 반환할 수 있다. [출처: Microsoft Azure Architecture Center, Gateway Aggregation pattern]
Gateway OffloadingTLS, Authentication, Rate Limiting, Logging, Caching 같은 공통 책임을 Gateway 계층으로 이동할 수 있다. [출처: Microsoft Azure Architecture Center, Gateway Offloading pattern]
운영 고려Gateway가 공통 진입점이므로 고가용성, 확장성, Timeout, 장애 격리와 관찰 가능성을 함께 설계해야 한다.

4. 예

Service Routing Example

Client → API Gateway → /api/users/* → User Service ├→ /api/orders/* → Order Service └→ /api/ai/* → AI Service
# conceptual routing
/api/users/*   -> User Service
/api/orders/*  -> Order Service
/api/ai/*      -> AI Service

Client는 각 Service의 내부 Host와 Port를 직접 관리하지 않고 Gateway Endpoint를 사용한다. Service 배치가 변경되더라도 외부 API 계약을 유지하도록 Routing 계층을 독립적으로 관리할 수 있다.
